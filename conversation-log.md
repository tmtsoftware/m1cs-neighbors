# Neighbors Project — Conversation Log

A record of the conversation that produced the `neighbors` mirror-segment
library (the `neighbors()` function, its supporting data model in
`src/neighbors/`, and the tests in `tests/test_neighbors.py`).

This is a summary transcript: user messages are reproduced verbatim, and
assistant turns are condensed to the substantive explanations and
decisions (the many intermediate tool calls — image cropping, OCR
attempts, geometry computations, test runs, etc. — are described rather
than reproduced blow-by-blow).

## 1. Assistant

Investigated `Mirror2.png` to build the segment/neighbor model precisely.
Initial attempts to read segment labels via OCR (tesseract, various
preprocessing) were unreliable, so the approach shifted to pure image
geometry: using connected-component analysis on the mirror figure to get
the exact pixel centroid of every one of the 492 hexagon cells, then
fitting a hexagonal lattice to those centroids to recover precise axial
hex coordinates for every segment. Two independent methods of computing
adjacency (pixel-distance thresholding vs. pure lattice-coordinate
neighbor offsets) were cross-checked and found to match perfectly across
all 492 segments, giving high confidence in the resulting adjacency
graph.

## 2. Assistant

Fetched the suggested redblobgames hex-grid library for reference (cube
coordinates, unit neighbor directions, 60° rotation). Using the
segment-position data already extracted from the image, derived sector
A's exact layout as a closed-form rule:

- Rings 1–10 are "full" rings: ring *i* has *i + 1* segments.
- Ring 11 is short one segment (missing the position closest to sector
  B).
- Ring 12 is a truncated 6-segment ring sitting in the angular middle of
  the sector (the mirror's outer edge is roughly circular rather than a
  perfect hexagon, so the outermost ring only exists partway around each
  sector).

Confirmed sectors B and C are exact 60°-rotated copies of sector A (by
comparing coordinates and by visually spot-checking crops of the image),
so sectors D, E, and F are generated by rotation rather than re-deriving
their geometry from scratch.

Implemented the model:

- `Hex(q, r, s)` — a frozen dataclass for cube coordinates, with vector
  addition and a `rotated_left()` 60° rotation.
- `SEGMENT_TO_HEX` / `HEX_TO_SEGMENT` — dictionaries mapping every
  segment id (e.g. `"A15"`) to its `Hex` location and back, built once at
  import time from the sector-A formula plus rotation.
- `neighbors(segment_id)` — looks up a segment's `Hex`, checks the six
  standard hex-grid neighbor directions, and returns the segment ids (if
  any) found at each of those locations.

Validated the result against the two facts given in the project's
CLAUDE.md (`A15`'s neighbors are `A10, A16, A21, A22, B20, B27`; `A77`
has only 3 neighbors: `A68, A69, A78`) — both matched exactly — plus
internal-consistency checks (492 unique segment ids, each sector
numbered 1–82 with no gaps, neighbor degree only ever 3/4/5/6, and
neighbor relationships symmetric in every case).

  `SEGMENT_TO_HEX`/`HEX_TO_SEGMENT`, and the `neighbors()` function.
- **`__init__.py`** — a thin re-export of the public API, plus `main()`
  for the package's script entry point.

still passed.
